# Local Penpot delay: findings and remedies

Date: 2026-11-06. Status: investigation complete; isolated patch tested, live application pending. Scope: consumer design tooling. Madar runtime, API, packages and Design are N/A; the app runtime and reviewed engine pin remain unchanged. Existing design agents continue their own work. ## Findings

Two faults had already interrupted the work. Earlier receipts record 25 `java.lang.OutOfMemoryError: Java heap space` occurrences with a 1,549,795,328-byte heap maximum. The other thread increased the maximum to 3 GiB and proved two saved, reopened artwork exports. The exporter also imposed a 10-second element-readiness limit despite a measured 12.9-second `get-page` request. The other thread changed that limit to 45 seconds. These are prior repairs, not changes made by this investigation. See [heap recovery](2026-11-06-penpot-backend-heap-recovery.md) and [exporter recovery](2026-11-06-penpot-exporter-readiness-recovery.md).

The document places a large workload on the local runtime. Frozen archive 111b contains 89,735 shapes on one page: 42,890 paths, 40,260 groups, 6,401 rectangles and 66 frames, plus a few other types. Its ZIP occupies 184,425,762 bytes; its entries expand to 561,627,147 bytes. Path JSON accounts for 441,599,120 bytes. This is a frozen snapshot; the controller has since added artwork. Shape type alone does not establish that a path came from text or authorize deleting it. [Complexity receipt](../../outputs/penpot/completion/performance-investigation/archive-complexity.json).

The current runtime uses native ARM64 images in a dedicated 4-vCPU, 6-GiB Colima VM on a 16-GiB Mac. One backend snapshot showed 3.625 GiB of container memory and 115.24% CPU, while the exporter was idle. VM available memory was about 1.17 GiB. A second snapshot showed about 1.59 GiB of used JVM heap; cumulative GC time was 52.5 seconds since restart, with six full collections. These observations establish limited headroom, not a continuous GC stall or a need to increase the heap again. No cgroup OOM kill appeared. The recent captured 15-minute backend log had no heap exception lines.

Recent frontend access logs, from 18:14:17 to 18:28:06 UTC, include one successful `get-file` response of 101,241,481 bytes and one `get-page` response of 953,442 bytes. Fifteen `update-file` responses returned HTTP 200. Access logs do not include request duration, and HTTP 200 does not establish visual or saved-artwork correctness. Reloading the editor requires substantial transfer and decoding. Avoid unnecessary full navigation while retaining required persistence checks.

Parallel source preparation does not parallelize the shared editor. The parent dispatched ten Gemini source-check agents; one Codex controller retains the Penpot browser and file-write work. Its recent activity includes recovering nested settings boards, verifying root placement, saving, reopening and exporting. Those operations and content correction remain on the delivery path. Available records do not support a percentage split of all elapsed hours between server work, browser actions, review, recovery and coordination. Do not describe wall time as active effort.

## Source inspection and tested patch

Self-hosting supplies running container images. The installed backend JAR also contains Clojure source, but there is no full editable upstream development checkout in the examined deployment directory. This investigation extracted relevant source and verified `files.clj` and `files_update.clj` against upstream revision `f44566963daf61fce4d8608e7c5e8c27c5853a88`. Image tags are 2.18.5; the installed manifest reports 2.18.5-RC1.

In `get-page`, Penpot first removes thumbnails from all page objects and then selects the requested board subtree. Its ObjectsMap stores encoded entries and decodes them on access. That ordering forces traversal and decoding of unrelated shapes before discarding them. The proposed three-line patch selects the subtree first, then strips thumbnails. It keeps permissions, validation, page loading and the no-object-ID full-page result unchanged. [Exact upstream source](https://github.com/penpot/penpot/blob/f44566963daf61fce4d8608e7c5e8c27c5853a88/backend/src/app/rpc/commands/files.clj), [patch](../../outputs/penpot/completion/performance-investigation/get-page-prune-first.patch).

The isolated harness uses the installed JAR's real helpers and evaluates the original and patched source expressions. Four tests with 25 assertions pass, including UUID and multiple-ID selection, unknown IDs, empty selection, overlapping selection, missing child references, guarded cycles, hidden shapes, missing thumbnails, native ObjectsMap and input preservation. An independent reviewer reran the suite and found no blocking patch issue.

The first synthetic plain-map benchmark used 89,735 objects, a 400-object selection and 30 alternating samples. Median filtering time was 8.19 ms before and 0.47 ms after. A second benchmark gave each variant a fresh serialized ObjectsMap decode cache: 15 alternating samples measured median 586.92 ms before and 2.97 ms after; p95 was 1,013.47 ms and 33.20 ms. With 15 samples, that p95 is the largest sample. These tests measure the filtering step on synthetic shapes, excluding database access, file/blob loading, network, browser rendering and saving. They do not prove a live export speedup or establish how much of the observed delay comes from this code. The full JVM process used about 503 MB maximum RSS. [Tests, commands, JVM/JAR identity and measurements](../../outputs/penpot/completion/performance-investigation/diagnostic-receipt.json).

The installed revision already contains affected-page integrity validation. Upstream [issue 12602](https://github.com/penpot/penpot/issues/12602) describes broader save optimizations, but its all-page-validation description is not proof of a missing fix here. The snapshot path can realize file data when enabled; this investigation has not established automatic snapshotting as an active cause. Do not disable validation, backups or history to gain speed.

## Remedy sequence

1. Preserve the working 3-GiB heap setting and prove the exporter readiness override survives future container recreation. The current exporter patch lives only in its writable container layer. Prepare a fingerprinted derived image or mounted override, with a quiet-boundary recreation and rollback test. No recreation occurred in this investigation.
2. Measure one representative save and export by stage: request queue/lock, file/blob loading, change application, encoding/persistence, render readiness and screenshot. Collect only timing/counters. Do not enable broad debug logging or expose payloads. Current access logs cannot establish the largest stage.
3. Apply the small export patch to an isolated build or disposable fixture instance, then compare original/patched native PNG/SVG, IDs, layers, crops and full-page export behavior. Only after this passes should the controller schedule live adoption. The patch passed isolated tests and independent review; server build and actual-file export parity remain pending.
4. Limit further growth: reuse stored IDs, reconcile unknown outcomes before import, and correct only affected artwork. Preserve historical work. A smaller active document, separate phase pages/files or reduced path/group count may provide a larger improvement, but the current canonical single-page rule prevents unilateral reorganization. Native text or path deduplication also needs appearance and Arabic shaping checks before adoption.
5. Keep parallelism in preparation and independent review while one controller performs sequential visible UI writes. More agents cannot remove that serial dependency. Any future batch tooling must preserve the owner's local-browser workflow, revision identity, save/export evidence and approval gates.

No live source patch, service restart, image upgrade, database write, artwork mutation or app/engine change occurred in this investigation. [Detailed operational record](2026-11-06-penpot-performance-investigation.md).
