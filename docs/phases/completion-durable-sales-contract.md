# Isolated durable sales composition contract

Status: authorized isolated implementation under ADR 0021 and the Completion plan. This is a candidate command layer; it does not activate schema 12 in the running app or approve live opening values, a cutover date, migration, UI or delivery.

Madar owns immutable balanced values, exact calculations, durable identity/replay coordination and the existing single document-store protocol. Dakhl_Restaurant owns source-record proposals, restaurant mapping, envelope composition, captured account intent and source-to-journal reconciliation. Consume reviewed engine d316fd6076375daa3f412889f73eaebfeeb5d4d4. Engine implementation is N/A unless a concrete missing reusable capability is demonstrated; report that gap before duplicating shared behavior.

The next vertical slice covers a completed sale, a partial/full return and an eligible sale void against an already initialized synthetic PortableJournalState. Reuse SaleProposal, ReturnProposal, RestaurantJournalMapper, PortableJournalCodec and the public DurableCommandCoordinator. One store owner must atomically persist the validated source candidate, its journal/provenance and receipt/outcome. No second journal database, copied coordinator algorithm, repository bootstrap change or live account path belongs in this slice.

Commands bind an explicit caller-owned account lineage, captured expected storage fence, operation identity, journal/source identities and recording time. Freeze caller inputs before async work or notifications. Derive a versioned canonical payload identity from the complete submitted command; changes to any financial or intent field must reject replay without writes. A canonical JSON identity is acceptable for the isolated slice when deterministic, bounded and documented; do not copy a hash algorithm or import an undeclared transitive package. Journals and receipts remain within the existing complete-state capacity bound. Lineage must be checked before receipt replay as well as before proposal evaluation and after rereads; a proposal-only check is insufficient because replays skip proposals.

Persist the mapper's source type/record identity, source version, receipt number, exact financial snapshots and reversal/correction links. Portable metadata accepts JSON values; compose BigInt snapshots as explicit exact decimal strings without altering the mapper/domain values. Preserve prior journals/receipts and unrelated account records, and retain stable outcomes across reopen, uncertain acknowledgements and replay. Never rewrite posted journal history or fabricate a missing original posting.

Gated or incomplete cutover state refuses posting. Established cutover in tests is synthetic evidence only. Operations before the cutover, or returns/voids whose historical source has no eligible post-cutover journal, must fail closed under the unresolved cross-cutover gate. Preserve source-permitted negative cash; do not invent tax, COGS, inventory valuation, cashbox or supplier movements. Sales use approved net revenue; returns use the separate refund account on the return date; voids use the original date and reject any sale with returns. An explicit zero-compatible mapping profile may preserve codec-valid zero outcomes; do not silently reject valid historical values or invent positive postings.

Tests must prove source/journal/outcome reconciliation, unchanged state on all rejected paths, account-lineage and fence isolation before replay, changed payload/version rejection, frozen input, zero handling, over-return and void eligibility, original-date inverses, preservation of prior history, real-store close/reopen and uncertain-ack resolution. This slice does not claim arbitrary crash-boundary or multi-process writer safety. Existing codec/C1 reviewed files remain unchanged; implementation and focused tests use new owned files. Independent review precedes consumer adoption. F-05–F-10 and C2/C3 checklist closure require their remaining integration, reconciliation, native, benchmark and delivery evidence.
