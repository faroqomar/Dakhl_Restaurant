# Deleted spending restoration

Authorized source undo extension under ADR0021 examples D/F, following the initial session controller. App-owned source/journal mapping; Madar changes/revision N/A. Existing reviewed host, exact source codec and mapper supply the required generic capabilities. No live activation, default counteraccount or inverse-of-inverse.

`RestoreDeletedSpendingCommand` supports expense, transfer and explicitly mapped external cash. It captures operation/new replacement IDs, original source ID/version11/snapshot, deleted active journal, deletion inverse and committed deletion operation, reason, recorded timestamp, fence/lineage and mapper context. Original list position and expected sibling IDs restore source ordering while guarding the affected collection. Source note, funding/type/category/date and `createdAt` must match the retained deletion snapshot exactly. No arbitrary new source amount or classification enters a restoration.

`DeletedSpendingRestorationCoordinator` borrows the existing `JournalCommandHost`. It validates the deleted family, exact reasoned delete receipt/target/inverse, absent source, original-date eligibility, expected sibling list and canonical candidate. Transfer restoration rechecks available remaining cash. External cash requires explicit accepted mapping; mapping must reproduce the deleted posting's exact journal value. No unverified pre-cutover/missing-original reconstruction occurs.

Restoration appends one new replacement journal with `correctedFromJournalId` referencing the deleted active journal. The old journal and deletion inverse remain byte-equivalent in value. The new journal has no `reversesId`. Each family validator recognizes this receipt-backed edge after a validated deletion, reactivates the new posting, then validates later edits/deletes/restorations. Old create/delete/restore operations replay retained historical outcomes through the complete family. Exported portable state retains all trails and receipts.

`SpendingOperationsViewModel` exposes `restoreDeletedIntent`, `previewDeletedRestoration`, `submitDeletedRestoration` and exact pending `retry`. `SpendingSessionUndoAdapter` now maps the supported deleted-source actions into that API. The existing session controller pops only after acknowledged success/replay. Other unsupported/structural full-source restorations still refuse with the stack intact; no whole-envelope rollback exists. Root owns observer/undo UI composition.

Executed: five new focused restoration cases plus five session-undo successor cases passed together. Three cases restore each family, edit/delete again and replay old create/delete/restore operations without writes. Other cases reject wrong deletion/source/siblings and reconcile an unknown restoration using the same command. Scoped analysis of the eight affected files is clean after style-only fixes. At this focused checkpoint, broad review/full-suite/benchmark/native/visual acceptance remained deferred. The later [successor closeout](../log/2026-11-08-remaining-completion-closeout.md) records completed local full-suite, native and benchmark checks while preserving visual/physical and release gates.

Source-local successor: ordinary create/edit/delete undo now validates only the affected source/family and previews its restore over current unrelated source. Optional SourceRecordOrder is identity-bearing only when supplied; evaluators and history parsers preserve original row order without altering old command identities.
