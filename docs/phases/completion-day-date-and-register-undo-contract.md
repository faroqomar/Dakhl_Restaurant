## Source date range

`DayDatePlan` selects recorded dates exactly from nonempty/observed day objects plus payment/transaction/transfer dates. One common UTC offset maps the selected range, rejecting invalid/missing start dates and targets occupied by records outside that selected range. It builds the whole day map before publication. Payments, transactions and transfers move; invoices, sales, returns, inventory, debts and worker records keep their independent dates. Embedded correction dates stay unchanged. A moved remaining snapshot adjusts only its sales baseline by target sales minus original sales; recorded balance stays fixed.

`DayDateCorrectionCommand.capture` freezes complete expected source, canonical complete-state SHA256, captured revision/fence/lineage, mapping, reason, mapper context and ordered child intents. Existing eligible expenses, supplier payments and transfers receive original-date inverses and target-date replacements. Mapped external cash additionally requires the caller's explicit accepted counteraccount to match its retained original mapping. Raw/unmapped external cash, missing/ambiguous/invalid original postings and cross-cutover financial moves refuse the entire operation. Existing family validators and mappers prove the original and replacement chains; source validation checks the final payment/invoice/debt timeline after all records have moved together. No source-only rewrite of a posted record is allowed.

The operation writes one complete candidate with one real parent receipt. Child intents/outcomes/entry snapshots travel in the parent evidence. `correctionReceiptViews` reconstructs read-only child views bound to the parent's exact intent/outcome, source transition, lineage, fence, revision and sequence. It verifies retained exact entry values and rejects child operation ID collisions. It does not persist pseudo receipts. Family validators consume these views, so original create replay and subsequent corrections remain executable. The day-date coordinator separately rebuilds mapper evidence on replay and validates the current complete family chain, allowing historical outcomes after later compensation without requiring the old source state to remain current.

The optional `JournalCommandHost.expectedRevision` guard checks a newly attached receipt before encoding/write, including rejection receipts. Equal-payload rewrites at a newer captured revision therefore fail before persistence. Existing callers omit it and retain their identities. Historical replay validates the retained receipt without applying the new-attach guard. Optional transfer `newDate` is omitted from old amount-only payloads; independent transfer date submission returns `date_shift_batch_required`. Atomic day batches alone supply the complete target-day/source proof.

## Public composition

`DayDateCorrectionController` borrows store/snapshot and explicit peer-write exclusion, with optional acknowledged-snapshot callback and accepted external-cash counteraccount. It exposes `preview`, `capture`, `submit`, `retry`, `acceptSnapshot`, account/snapshot, busy/readback/error state. Unknown acknowledgement retains the captured command. `RestaurantOperationsSession.dayDates` joins peer exclusion, source synchronization, listeners/disposal and import guarding over the same store; dirty settings remain staged and stale source cannot overwrite them. ## Session undo

`DayDateSessionUndoAdapter(dates, identity)` captures a new inverse date operation. Optional `inverseOf` plus `exactMapping` fields are accepted only together and bound to an earlier retained committed receipt, its validated mapping/source/history and a strictly earlier receipt sequence. They invert the exact selected dates, so sparse gaps remain untouched. The affected date/source set and active postings must match retained evidence; unrelated current archived products, stock reversals and metadata remain intact. The inverse retains source correction trails with the frozen compensation reason. Ordinary commands omit these fields and retain their prior identity. Every new inverse still captures the current complete envelope digest/revision and receives the same financial/cutover/history validation. It does not overwrite an old envelope or remove any journal/receipt.

`DailyRegisterSessionUndoAdapter(register, identity)` uses the existing register owner's busy/pending/readback/snapshot lifecycle. A sealed `RestoreDailyRegisterCommand` and evaluator restore only captured remaining/balance/total fields, including the full original remaining baseline. They require retained original command/outcome proof and exact current values for the original action’s affected fields (balance; total override; or remaining plus balance), then validate the complete restored account and preserve all financial journals and receipt history. Unrelated current fields/artifacts remain intact. A complete captured source/revision precondition still protects the compensation after preparation. Source `preserveCorrectionTrail` behavior keeps current correction entries and appends the frozen undo reason when restoring a changed observed balance/total. Empty day scaffolding retained for audit is excluded from source-effect comparison. This is a register observation compensation, not cash flow, profit, an opening adjustment or a financial journal.

Adapters are session-local and feed the existing capped undo stack. Failed/unknown operations keep the undo position; retries reuse the same captured operation. No recoverable undo stack across restart was introduced. Root owns app dispatch and native UI evidence.
