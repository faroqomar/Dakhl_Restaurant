# Purchase proposals

Status: the pure proposal API returns hypothetical candidates without writing. The current invoice preview/payment-allocation UI and durable spending commands consume these candidates; journal-backed submission and repository commits belong to those callers. See the [current successor closeout](../log/2026-11-08-remaining-completion-closeout.md).

`PurchaseProposals` composes immutable account candidates from a codec-validated baseline. The caller supplies IDs and timestamp; no random generator, clock, storage or side effect exists. Returned records require separately approved journal mappings, atomic persistence and stale-fence handling before any save flow can consume them.

Invoice proposals preserve saved name/unit/price snapshots, per-supplier Latin-digit invoice-number uniqueness, independent carton/piece values and inline material creation. Material name matching uses the explicit engine Unicode17 lowercase profile after source digit normalization; existing archived materials remain matchable exactly as source readInvoiceLines. Existing catalog prices are not silently rewritten. Inline material, invoice and optional immediate payment appear in one returned validated document, or no candidate is returned. Failed validation never mutates the baseline.

Payment proposals use Madar allocation/funding calculations and existing supplier debt/invoice queries. Selected invoice receives payment first; remainder consumes eligible dated debt. References and dates are checked, edits exclude their previous payment from allocation and preserve original timestamp. Payments remain one payment record; derived expense/cash projections own its effect. No duplicate cash transaction is inserted. Paid invoice deletion and edits below allocated payments fail. Raw amount/quantity input parsing belongs to form/controller layers; this API takes parsed values and canonicalizes via LegacyAccountCodec.

Source oracle executes extracted frozen `supplierSubmit`, `readInvoiceLines` and `readPaymentFunding` functions with synthetic form adapters, fixed IDs/time, and actual model validation. It covers inline invoice plus shared immediate payment and debt-only cash payment. Separate rejection tests cover duplicate invoice number, paid deletion, reduced paid invoice, overpayment, early payment and invalid split funding; baseline remains unchanged. The original three test bodies pass in a pure-Dart runner; targeted analyzer passes. Test-first missing-API failures preceded implementation. Flutter/native tests remain pending under current disk constraint. This is representative coverage, not exhaustive purchasing acceptance.

Expanded frozen-submit oracle coverage now adds six scenarios: editing middle invoice/payment with preserved surrounding records and append order, payment supplier change to eligible debt, rejected paid-invoice reduction, rejected paid-invoice supplier change, and multiple lines reusing one new material plus an archived existing material. All nine pure-Dart test bodies pass; fixture provenance uses Electron Node-only runtime. No implementation mismatch was found by this expansion.

Potential further acceptance: source maximum-count fixtures, stale/durable commit failures and integrated receipts. Financial corrections/undo and opening/history journal mapping remain unresolved approval gates. No required checks are weakened.
