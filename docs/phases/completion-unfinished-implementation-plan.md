## Shared completion rules for the item plans

An M or I item closes only after the specified operational behavior, failure/retry/restart evidence and independent review exist at a named revision. A V item closes with the required real evidence, or an explicit owner scope decision recorded as excluded/N/A rather than passed. A G item closes only when the identified decision maker records the named decision, approval or access outcome; dependent actions remain pending until then.

For every later implementation batch, keep app and engine evidence/project banks separate and cross-link public contracts, exact adopted engine revision, tests and receipts. Existing package versions remain fixed during this planning task. Prefer current compatible reviewed packages; investigate official compatibility/licensing/offline behavior before any future dependency addition. Do not add unused dependencies or copy engine implementation into the app.

Preserve offline single-restaurant operation, Arabic RTL runtime UI, exact IQD/source rounding, historical values/IDs/snapshots and protected account data. No cloud/auth/multitenancy, Windows, grocery UI, recipes/kitchen/tables, purchase-to-stock conversion, camera scanning, thermal/Bluetooth/ESC-POS, tax/fees, customer credit, payroll, invented COGS/profit, day locking or store publication enters this plan. Retired worker/savings records remain compatibility data. Broader Madar supported-release gates remain outside consumer Completion.

No calendar or cost estimate is asserted: policy decisions, design qualification, platform access and implementation size require bounded discovery after the owner chooses the next work. The closure evidence required for each item is explicit without inventing durations or performance budgets.
