# Conditional external cash commands

App-owned completion backend and source-reference form. Madar changes/revision: N/A; the existing durable host, balanced journals and mapper suffice. Source: frozen `electron-reference/app/ui/renderer.js` transaction save/delete handlers, canonical schema11 codec, ADR0021 and `mapExternalCashAdjustment`. Implementation authorization does not approve an actual counteraccount, opening balance, live activation or release.

`SpendingOperationsViewModel(acceptedCounterAccountId: String?)` binds caller configuration. Null/blank mapping refuses `unmapped_financial_gap` without a write, including a rejection receipt. The VM also refuses a submitted command carrying a different mapping; coordinator callers must supply their own explicitly accepted configuration. The implementation selects no equity/revenue/purchase-expense default.

Public intent methods: `createExternalCashIntent`, `editExternalCashIntent`, `deleteExternalCashIntent`; `submitExternalCash` returns `DurableCommandResult<ExternalCashOutcome>`. Existing `retry()` retains the exact pending object. Intents capture operation/transaction/journal IDs, lineage, fence, mapping context and timestamp. Create/edit require positive IQD amount, deposit/withdrawal type, DateOnly and note. Corrections additionally require the exact expected source snapshot, active journal ID, inverse ID and user reason. Edit takes a replacement journal ID as `journalId`. Source note trims as in the frozen handler; edits retain original `createdAt`, remove the prior row and append the replacement. Delete removes the source row while retaining immutable receipt/journal history.

`RestaurantJournalExternalCashHistory.validate(state,id,mapper)` validates the committed command family, receipt identity/order/outcome, source snapshots and journal values/links. `activePosting(state,id,mapper)` returns the exact eligible current posting or null. Original-date inverses and selected-date replacements never erase journals. Old create/edit/delete receipts replay after later corrections/deletion. Stale source/fence/context, pre-cutover dates, missing original posting and conflicting IDs fail closed. Other workflows' date-batch history views do not yet include raw external transactions.

UI entrypoint: `showCashAdjustmentEditor(context,{SpendingOperationsViewModel? model, Map<String,Object?>? source, String initialType='deposit', ValueChanged<bool>? onPendingInputChanged})`. Null source creates; saved source enables conditional edit/delete. Missing configuration shows fields and a plain Arabic explanation with save disabled, without technical IDs or a mapping-selection UI. Corrections require a reason; deletion confirms. Unknown outcomes freeze captured inputs and offer exact retry. Dirty dismissal uses the existing discard dialog. Root owns daily/cash route wiring and explicit configuration composition; this step does not edit the shared session.
